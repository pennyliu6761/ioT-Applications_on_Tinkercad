## F3 系統整合

### 整合前檢查

開始合併電路前，先確認這六件事。**任何一項打勾不了，先回頭補，不要硬整合。**

| # | 檢查項目 | 為什麼重要 |
| --- | --- | --- |
| 1 | 每個子系統都照**腳位總表**接線 | 否則合併時腳位會撞在一起 |
| 2 | 腳位總表上**沒有任何一隻腳被兩個元件使用** | 最常見的整合失敗原因 |
| 3 | 需要調光、調速的元件，沒有接在被伺服（9、10）或蜂鳴器（3、11）借走的腳 | 單獨測試時可能沒發現（例如 S2 沒有蜂鳴器） |
| 4 | A4、A5 若給 I2C LCD，就沒有其他元件借用 | 單獨測試時可能沒發現 |
| 5 | 每個子系統的程式都註明來源（範例 A、B 或第幾週的哪個專案） | 整合時才知道去哪裡找 |
| 6 | 整合待辦清單已更新 | 知道還有哪些問題要處理 |

> 🔍 **第 3、4 項特別容易漏掉**：子系統單獨測試時，「搶資源」的元件可能根本不在同一個檔案裡。

### 整合五步驟

**不要一次把所有東西接上去。** 和子系統建置一樣，一次只加一個子系統：

| 步驟 | 做什麼 | 確認什麼 | 存檔 |
| --- | --- | --- | --- |
| ① 準備底板 | 從最核心的子系統（通常是有安全功能的那個）另存新檔 | 該子系統功能正常 | `FINAL-組別-v1` |
| ② 規劃麵包板 | 依下方「佈局原則」決定每個子系統放哪一區 | 電源軌全部連通 | — |
| ③ 逐一搬入 | 每次搬一個子系統的電路，**腳位照總表、不准改** | 搬完後打開它的功能開關，該子系統正常、**之前的子系統也還正常** | 每搬一個存一版：`v2`、`v3`…… |
| ④ 打開優先權 | 打開安全／總控相關的功能開關 | 優先權流程圖上的每一層都測一次 | `v4` |
| ⑤ 全功能確認 | 所有功能開關都打開 | 執行規劃書中的全部測試案例 | `FINAL-組別-整合版` |

> 📌 **版本存檔是救命繩**。整合到 v3 出問題時，你可以打開 v2 比較差在哪裡，而不是從頭找起。每個版本在檔名或說明欄寫下「這版加了什麼」。

### 麵包板佈局原則

整合版的元件很多，佈局決定了除錯有多痛苦：

```
┌─────────────────────── 麵包板（可用兩塊） ───────────────────────┐
│  ═════════ 5V 軌 ═════════════════════════════════════════════ │
│  ═════════ GND 軌 ════════════════════════════════════════════ │
│                                                                 │
│   【輸入區】               【晶片區】             【輸出區】       │
│   按鈕、旋鈕、              74HC595、L293D        LED、RGB、      │
│   感測器（10kΩ 放這）        （跨凹槽）            七段（220Ω 放這）│
│                                                                 │
│   【安全區】                                     【動力區】       │
│   急停鈕（放最顯眼的位置）                         伺服、馬達、繼電器 │
│                                                                 │
│  ═════════ 5V 軌 ═════════════════════════════════════════════ │
│  ═════════ GND 軌 ════════════════════════════════════════════ │
└─────────────────────────────────────────────────────────────────┘
```

| 原則 | 說明 |
| --- | --- |
| 輸入在左、輸出在右 | 訊號流向一目了然 |
| 同一個子系統放在一起 | 出問題時知道去哪一區找 |
| 上下電源軌都要接到 5V 和 GND | 很多「某一區都不動」的問題，是電源軌沒接 |
| 急停鈕放在最顯眼、最好按的位置 | 真實控制盤的急停也是這樣設計 |
| 動力元件（伺服、馬達、繼電器）集中一區 | 方便檢查電源線 |
| 線的顏色有規則 | 例如：紅＝5V、黑＝GND、其他顏色＝訊號 |

### 整合程式怎麼來

| 你的專題來源 | 整合程式的做法 |
| --- | --- |
| **改編範例 A 或 B** | 直接拿範例的整合程式修改：改設定區的腳位與規格、增刪子系統區塊 |
| **延伸某週 BOSS 關或自訂** | 照下方「整合程式骨架」，把各子系統程式的內容依優先權順序放進對應區塊 |

**整合程式骨架**（範例 A、B 都是這個結構）：

```cpp
// ===== 期末專題：（系統名稱） =====
// 組別：　　　組員：
// 子系統來源：S1 改自＿＿、S2 改自＿＿、S3 改自＿＿

#include <...>                     // ← 各子系統用到的函式庫全部放這裡

// ===== 設定區：腳位（照腳位總表） =====
// ← 各子系統的腳位全部集中在這裡

// ===== 設定區：客戶規格 =====
// ← 溫度線、距離、人數上限、角度、時間……全部集中在這裡

// ===== 功能開關：逐一打開 =====
bool useS1 = false;
bool useS2 = false;
bool useS3 = false;
bool useS4 = false;

// ===== 共用變數與工具函式 =====
// ← readC()、readCM()、showLine()、sendOut()、pressed() 等，各寫一次就好

void setup() {
  // ← 各子系統的 setup 內容合在一起
}

void loop() {
  // ① 讀取所有按鈕與感測器
  // ② 最高優先：急停／最高安全條件 → 成立就處理並 return
  // ③ 次高優先：安全連鎖、品質連鎖
  // ④ 模式判斷（HOA、營業／打烊……）
  // ⑤ 各子系統一般功能
  // ⑥ 更新看板（LCD、七段、狀態燈）
  delay(30);
}
```

> 💡 **工具函式只寫一次**：如果 S1 和 S3 都用到 `readC()`，整合時只保留一份。重複的函式名稱會讓程式無法上傳。

### 整合後常見問題

| 現象 | 可能原因 | 處理方式 |
| --- | --- | --- |
| 某個子系統單獨正常，整合後完全失效 | 腳位重疊；電源軌沒接 | 對照腳位總表；檢查上下電源軌 |
| 調光、調速失效 | 伺服或蜂鳴器借走了 `~` 腳 | 查「~ 腳可用表」，改接 5、6 或改用全亮全滅 |
| 程式無法上傳，出現「重複定義」 | 兩個子系統有同名的函式或變數 | 只保留一份，或改名 |
| 按鈕偶爾沒反應 | 其他子系統有很長的 `delay()`，按鈕被「錯過」 | 見下表「反應變慢」 |
| 優先權不對（例如急停後還有東西在動） | 程式區塊順序和優先權流程圖不一致 | 照流程圖調整區塊順序 |
| 看板數字怪怪的 | 計數只在「狀態改變的瞬間」做了嗎？ | 回顧第 5 週狀態改變偵測 |

**「反應變慢」怎麼處理？**（上週整合待辦清單常見項目）

整合後，某個子系統的 `delay()` 會讓整個系統「卡住」那段時間。不需要重寫程式，先用這幾招：

| 做法 | 例子 | 效果 |
| --- | --- | --- |
| 縮短等待 | 迎賓聲 `delay(1650)` → `delay(300)` | 大部分情況就夠了 |
| 把長動作放在「只會偶爾發生」的地方 | 開門、結帳時才等，平常不等 | 平常反應不受影響 |
| 把急停檢查放在長動作「之前」 | 開始一段 3 秒的動作前先確認沒有急停 | 至少不會在急停中啟動 |
| 寫進「已知限制」 | 「柵欄升降的 2 秒內，按鈕無效」 | 誠實告知客戶，列入下一階段改善 |

> 💡 真正的解法是用 `millis()` 讓系統「同時做很多事」（第 2、9 週都看過它）。這留給有餘力的組別當**加分項目**，並在提案中說明。

## F4 驗收測試（QA）

> 🏭 **為什麼要做 QA？** 你的系統在「正常操作」下一定會動——因為你只會用正常的方式操作它。客戶、現場人員、甚至是調皮的路人，才不會照你的劇本走。**QA 的目的，是在交給客戶之前，先替他們把所有不正常的操作都試一遍。**

### 六種測試類型

上週規劃書的第 7 項至少有 8 個測試案例。這週要擴充到**每一類至少 2 個、總共至少 15 個**：

| 類型 | 要問的問題 | 範例 A（冷鏈）的例子 | 範例 B（便利商店）的例子 |
| --- | --- | --- | --- |
| **① 正常流程** | 照設計的方式操作，結果正確嗎？ | 箱子通過 3 次，出貨數 +3 | 加入 2 項商品後結帳，金額正確 |
| **② 邊界值** | 剛好在門檻上、到達上限時呢？ | 溫度剛好 8.0°C；出貨數到 99 | 來客數到 99；商品編號 10、15 |
| **③ 同時觸發** | 兩件事同時發生，誰優先？ | 溫度異常時按急停 | 結帳中切換打烊 |
| **④ 誤操作** | 使用者按錯、按太快、亂按？ | 快速連按模式鈕 10 次 | 結帳中亂按 `*`、`#` |
| **⑤ 元件異常** | 某個感測器壞了（拔掉一條線）會怎樣？ | 拔掉 TMP36 的訊號線 | 拔掉 PIR 的訊號線 |
| **⑥ 長時間運轉** | 跑久了會不會出問題？ | 連續模擬 5 分鐘出貨 | 連續模擬 30 位客人 |

> 🔍 **第 ⑤ 類最容易被忽略、也最有價值**。在 Tinkercad 裡刪掉感測器的一條線，觀察系統怎麼反應：是「安全地停下來」，還是「繼續運轉卻做出錯誤判斷」？後者就是你要寫進報告的問題。

### 問題分級與缺陷紀錄

測試一定會找到問題。時間有限，不可能全部修完——**先修最重要的**。

| 等級 | 定義 | 例子 | 處理方式 |
| --- | --- | --- | --- |
| **P1 嚴重** | 安全功能失效、可能造成傷害或重大損失 | 急停後輸送帶還在轉；溫度異常還在出貨 | **展演前一定要修好** |
| **P2 重要** | 主要功能錯誤，但不影響安全 | 出貨數重複計算；結帳金額錯誤 | 盡量修好；修不好要寫進「已知限制」 |
| **P3 輕微** | 不影響功能的小問題 | LCD 文字被截斷；燈號顏色不夠清楚 | 有時間再修 |

### 同儕交叉測試

自己測自己的系統，很容易「手下留情」。所以每組要**交換系統，讓別組來找碴**。

**流程（約 30 分鐘）：**

| 時間 | 做什麼 |
| --- | --- |
| 5 分鐘 | 原組向測試組說明：系統功能、操作方式（**只說這些，不說哪裡有問題**） |
| 20 分鐘 | 測試組自由操作，至少完成**5 個自己設計的測試**，並從下方「刁難題庫」選 2 題 |
| 5 分鐘 | 測試組回報發現的問題，原組記錄進缺陷紀錄表 |

**刁難題庫**（測試組可從中選題，也可以自己出題）：

| 類型 | 刁難問題 |
| --- | --- |
| 優先權 | 「急停和安全連鎖同時觸發，系統會怎樣？哪一個先解除才能恢復？」 |
| 優先權 | 「我在手動模式下，安全條件還有效嗎？」 |
| 邊界 | 「計數到上限之後會怎樣？歸零？停住？還是出錯？」 |
| 邊界 | 「門檻剛好等於設定值的時候，算觸發還是不觸發？」 |
| 誤操作 | 「我一直狂按同一顆按鈕，系統會不會亂掉？」 |
| 誤操作 | 「如果我跳過某個步驟，直接做最後一步呢？」 |
| 元件異常 | 「如果這顆感測器壞了，系統會停下來，還是繼續用錯誤的數字做判斷？」 |
| 失效安全 | 「如果 Arduino 突然斷電，每個繼電器、馬達會停在什麼狀態？這安全嗎？」 |
| 擴充 | 「客戶明年要加一倍的設備，你的腳位還夠嗎？」 |
| 管理 | 「看板上的 KPI，管理者看到之後會做什麼決定？」 |

**測試組要交一份「交叉測試回饋單」：**

| 項目 | 內容 |
| --- | --- |
| 測試的組別／系統 | |
| 我們設計的 5 個測試與結果 | |
| 我們選的 2 題刁難題與系統反應 | |
| 發現的問題（請標註建議等級 P1／P2／P3） | |
| 這套系統最讓我們印象深刻的設計 | |

### 二、效益估算

用客戶的痛點來估算「每年能省下或賺到多少」：

| 效益項目 | 估算方式 | 範例 A（冷鏈） | 範例 B（便利商店） |
| --- | --- | --- | --- |
| 避免損失 | 事故發生機率 × 每次損失 | 每年 1 次整批報廢 × 20 萬元 | 冷藏櫃異常每年 2 次 × 3 萬元 |
| 節省人力 | 省下的工時 × 時薪 | 人工巡檢每天 1 小時 | 尖峰結帳每天省 2 小時人力 |
| 節省能源 | 省下的電費 | — | 招牌燈白天自動關 |
| 提升營收 | 增加的產能或客數 | 出貨效率提升 | 結帳等待縮短，減少顧客流失 |

### 三、回收期

```
回收期（年）＝ 系統總成本 ÷ 每年效益
```

> 🤔 估算一定有很多假設。**重點不是數字精準，而是把假設寫清楚**，讓客戶知道「如果你們的狀況跟我們假設的不一樣，結論會怎麼變」。

## F5 客戶提案展演

### 展演形式

每組 **10 分鐘簡報＋5 分鐘問答**。台下的老師和同學扮演「**客戶的決策會議**」——老闆、現場主管、財務、安全管理員。

| 段落 | 時間 | 內容 | 給誰聽 |
| --- | --- | --- | --- |
| 1. 客戶痛點 | 1 分鐘 | 客戶現在遇到什麼問題？不解決會損失什麼？ | 老闆 |
| 2. 解決方案 | 1.5 分鐘 | 系統架構圖：有哪些子系統、各自解決哪個痛點 | 老闆、現場主管 |
| 3. 現場展示 | 3.5 分鐘 | Tinkercad 操作：**正常流程 → 異常情境 → 緊急情況** | 現場主管 |
| 4. 安全與品質 | 1.5 分鐘 | 安全設計、失效安全、QA 測過什麼、還有哪些已知限制 | 安全管理員 |
| 5. 成本效益 | 1.5 分鐘 | BOM 成本、效益估算、回收期 | 財務 |
| 6. 下一步建議 | 1 分鐘 | 擴充空間、下一階段可以做什麼 | 老闆 |
| 問答 | 5 分鐘 | 台下「客戶」提問（可以使用刁難題庫） | 全體 |

### 簡報規則

| 規則 | 說明 |
| --- | --- |
| **不准講程式碼** | 客戶在乎「店員按這顆鈕會發生什麼事」，不在乎 `if` 和 `else` |
| **技術名詞要翻譯** | 「安全連鎖」→「有人靠近輸送帶時，它會自動停下來」 |
| **誠實說明已知限制** | 「柵欄升降的 2 秒內按鈕無效」——比被客戶當場抓到好得多 |
| **數字要有來源** | 「每年省 20 萬」要說明怎麼算的 |
| **展示要有劇本** | 事先排練好操作順序，誰負責講、誰負責操作 |

### 台下「客戶」評分單

每位同學評 2～3 組（老師指定），每項 1～5 分：

| 評分項目 | 我是…… | 1～5 分 |
| --- | --- | --- |
| 我聽懂了這套系統要解決什麼問題 | 老闆 | |
| 展示的功能真的能解決現場的問題 | 現場主管 | |
| 我相信這套系統出狀況時是安全的 | 安全管理員 | |
| 成本效益的說明讓我願意考慮投資 | 財務 | |
| 如果我是老闆，我會買這套系統 | 老闆 | |
| 一句話建議 | | |

| # | 觀念 | 一句話 |

## 📖 本週詞彙表

| 名稱 | 白話解釋 |
| --- | --- |
| 系統整合 | 把各自正常的子系統合在一起，並讓它們協同運作 |
| 版本管理 | 每完成一個階段就存一個版本，出問題時可以退回比較 |
| 驗收測試（UAT） | 依照事先寫好的預期結果，驗證系統是否符合需求 |
| 邊界值測試 | 測試剛好在門檻上、到達上限時的行為 |
| 缺陷分級（P1／P2／P3） | 依問題嚴重程度排定修正順序 |
| 已知限制 | 目前沒有修正、但誠實告知客戶的系統限制 |
| 交叉測試 | 讓不熟悉系統的人來測試，找出設計者沒想到的問題 |

| 回收期 | 系統投資要多久才能用效益賺回來 |
| 矯正措施 | 修正問題並找出原因，避免再次發生 |

## 反思與延伸討論

1. 整合時最常遇到的問題，往往不是「某個子系統壞了」，而是「子系統之間互相干擾」（搶腳位、搶資源、優先權衝突）。這和組織中「各部門各自做得很好，合在一起卻出問題」有什麼相似之處？
2. QA 測試中，「元件異常」類型的測試常常發現最嚴重的問題。為什麼設計者通常不會主動去想「如果感測器壞了怎麼辦」？在管理上，要怎麼讓團隊願意主動找自己的問題？
3. 期末提案要求「誠實說明已知限制」。有人會擔心這樣客戶就不買了。你怎麼看？誠實揭露限制，對長期的客戶關係有什麼影響？
4. 回顧整學期，從第 3 週「一顆燈接哪隻腳」，到期末「18 隻腳怎麼分給 13 種元件」。你覺得這門課教的是「Arduino」，還是別的東西？
